# Risk tiers for changes

Use this page to decide how closely to review a pull request.
It maps each part of the repository to a risk tier and gives the reason.
The QA pages in [docs/qa/](qa) own the checklists.
This page does not repeat them. It tells you which page to read and what evidence to ask for.

## How the tier is set

A change gets the highest tier of the paths that it touches.
If two rows match one file, use the higher tier.
The tier comes from what the repository does with the change:

- **High.** The change can run with a write token or a secret before review.
  Or the change can merge or publish with no person.
  Or the change sets the release of every package, the admission level of a namespace, or a privileged workload.
- **Medium.** The change gets to consumers through a release or a Git URL.
- **Low.** The change makes no release, holds no write token and no secret, and changes no auto-merge rule.

Each pull request to `main` needs the approval of a code owner. An organization admin and the Renovate app can bypass this rule. See [Rules on main](security/SECURITY-AI.md#rules-on-main).
Branch protection requires no image check, and it does not require the tests for `kube-vip-wireguard` and the five Pod Security components.
To see the current required checks, run `gh api repos/marinatedconcrete/config/branches/main/protection/required_status_checks --jq .contexts`.

## Map

The file [`.github/policies/paths.json`](../.github/policies/paths.json) holds this map as data.
A workflow runs for a pull request from a branch in this repository when the pull request opens, changes, reopens, or has its title or body edited. A pull request from a fork gets no labels, because its token is read-only.
GitHub does not run the workflow while the pull request has a merge conflict, so the labels can be from an older commit.
Do not use the labels until the workflow completes for the last commit after a person resolves the conflict.
The workflow adds one `area/` label for each area and one `risk/` label for the highest tier of the changed files.
It also removes `area/` and `risk/` labels that no longer fit, even a label that a person added by hand.
If the pull request has more than 3000 files, the workflow sets `risk/high` and stops.
A path with no rule counts as High.
`just path-policy-lint` fails when no rule covers a tracked file or when a glob matches no tracked file.
Change the table and the file in the same pull request.
Create the `area/` label in the repository before a rule uses a new area. The workflow does not create labels.
The label uses only the path. It does not use the exception in a row, such as "High if the change lowers the level".
The labels are advisory. The workflow runs the policy of the pull request, so a pull request that changes the policy can change its own label.
Use the labels to find pull requests. Use this map to set the review tier.
Keep these labels out of automated review and merge rules.

## What merges with no review

The root `renovate.json` lets Renovate merge these updates with no person.
Most of these rules use a branch merge, which has no pull request.
The image workflows then run only after the merge.
The Renovate app can bypass the ruleset on `main`, so a branch merge needs no approval.
The `prettier`, `pnpm`, `cli/cli`, and `node` rule uses GitHub auto-merge on a pull request. This repository has not yet seen if GitHub auto-merge uses the bypass of the Renovate app. Thus these pull requests can wait for the approval of a code owner.
When the update is in a release path and its commit type is not `test`, Release Please then opens or updates a release pull request. `ansible/requirements.txt` is not in a release path, because the `ansible` package excludes it.

- Patch updates of each dependency. Third-party actions and the images from the registries below are exceptions.
  The default wait is three days after the release. The `k3s`, `renovate`, and `devcontainer-base` rules below set a different wait or a schedule.
- Minor and digest updates of the Docker Hub images in `factorio`, `mosquitto`, and `unifi-network-application`.
  In `unifi-network-application`, these images are `busybox` and `mongo`. The `mongo` image stays below 8.1.0.
- Monthly Debian digest updates in `images/vscode-ssh-server/Dockerfile`.
- Patch updates of `k3s-io/k3s` and `kubernetes/kubernetes` in all files, one week after the release, on the 14th and the 28th day of the month.
- Digest, minor, and patch updates of GitHub's own actions (`actions/*`).
- All updates of the packages named `prettier`, `pnpm`, `cli/cli`, and `node`, and the monthly `renovate` update.
  `pnpm` stays below version 11. The `node-version` input of `actions/setup-node` has the package name `actions/node-versions`. Thus this rule does not apply to it, but the rule for GitHub's own actions does. A minor or patch update of that input merges with no person.
- New `devcontainer-base` releases, after all pull request checks pass.

Images from `ghcr.io`, `quay.io`, `registry.k8s.io`, and `lscr.io` never auto-merge, except `devcontainer-base`. Its rule is the last item in the list above. Third-party actions never auto-merge.
The registry rule comes after the `kube-vip` and `samba` rules. Thus those two rules do not cause an auto-merge.
The registry rule also comes after the Unifi rule. Thus the Unifi rule does not auto-merge the `lscr.io` image, but it still auto-merges `busybox` and `mongo`.
The monthly Fedora digest rule for `images/kairos-fedora` does nothing now. Another rule stops Renovate from pinning Fedora digests, and the Containerfile has no Fedora digest.
A change that adds an item to this list is a High change.

## What to ask for in each tier

These items are recommendations. Of these items, the repository enforces only the approval of a code owner.

- **High.** Ask a maintainer to review. Ask for the Manual QA results of the QA page in the `## Testing` section.
  Examples are a Renovate dry run for a rule change, a two-node cluster test for `kube-vip`, and the `e2e.sh` result for `kairos-fedora`.
  For a workflow change, read each `permissions` block and each use of a secret in the diff.
- **Medium.** Ask for the test command of the part and its result, for example `just kustomization-test <component>` or the image smoke test.
  Check the commit type against the release effect.
- **Low.** Check the wording against [AGENTS.md](../AGENTS.md). Confirm that the change makes no release.
  One approving review is enough.
